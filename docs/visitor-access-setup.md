# Visitor access rollout

This is a reviewable configuration/runbook, not evidence that visitor protection is active. Start from [visitor-access-config.json](visitor-access-config.json). Its replacement IDs are deliberate activation blockers; never submit it wholesale to an API. No OAuth clients, providers, visitor applications or WAF rules were created by this branch. The supporting-code milestone stops before deployment or live activation.

The desired policy offers Google OR Microsoft sign-in as alternatives for ordinary US visitors, with Cloudflare additionally offered only if an isolated visitor provider is supported. Access authenticates at the edge; the app does not manage visitor passwords or a second visitor JWT service. Country restrictions use Cloudflare's network geolocation, not citizenship, and deny non-US and unknown-country requests. Existing authenticated sessions must still be blocked outside the US by WAF.

## Prerequisites that currently block activation

1. Inventory and export all existing Access applications, provider settings, policies, zone rules/redirects and Pages aliases. Record IDs, AUDs and a digest of the redacted snapshot alongside the final desired configuration. The initial read-only snapshot is `reports/security-access-cloudflare-baseline.json` (ignored; retain securely with task evidence). Re-read before applying to detect concurrent changes.
2. **Provider inheritance is a blocker.** Municipal preview `6b52727c-5d1a-46c3-8c96-248601006162` and production `7dcaf0bf-6fcd-44ca-ad80-d5fcd015d858` have empty `allowed_idps`, which inherits newly registered providers. Do not create Google/Microsoft providers until the owner separately authorizes and validates pinning those unrelated apps, or approves an isolated organization design. That additional scope is not implemented here. Do not silently broaden their login methods.
3. The existing Cloudflare IdP `a4b44d0e-654a-44f8-9caa-f6cadc52520f` has `restrict_to_account_members: true`; keep it unchanged. Do not broaden it for visitors. Verify whether a second Cloudflare provider is supported and can be isolated before offering Cloudflare visitor login. If unsupported, record that provider as unavailable and resolve the user preference before activation.
4. Human sign-in to Google Cloud Console and Microsoft Entra is required to register OAuth clients. Configure exact Cloudflare callback URIs from the provider setup screen; store secrets only in the provider configuration. Google must allow intended external users and leave test-only restrictions only if explicitly accepted. Microsoft must support the intended personal and work/school account types through a Cloudflare-supported configuration. A tenant UUID does not prove both work; do not guess that `common` is supported. Require successful independent personal/work account tests before claiming either. Use login-only identity scopes; no mailbox, calendar, group or `Directory.Read.All` permissions are needed for this portfolio policy.
5. Seat capacity remains **UNVERIFIED**: the read-only inventory found one active Access seat; subscriptions returned HTTP 403 without billing-read scope. Verify the actual plan, remaining capacity, anticipated visitor volume and free capacity before activation. No paid upgrade, seat removal or shared expiry changes are authorized.
6. Complete local quality and fresh high-risk review for the exact candidate. Google/Microsoft setup, provider isolation, capacity, US/non-US tests, Cal geography, cookie behavior, alert routing and recovery exercise remain release blockers even if supporting code passes.

Both visitor and owner API applications set `options_preflight_bypass: true`. Do not combine it with `cors_headers`: the Worker supplies exact-origin CORS and credentials, and disallows foreign preflight. OPTIONS returns no records. Actual protected requests still traverse Access. Cloudflare application fields are `eager_redirect_cookie_setting`, `path_cookie_attribute` and `http_only_cookie_attribute`; preserve unrelated settings when updating existing apps. Do not replace existing owner apps or change the Worker owner AUD/email/issuer checks.

Add the manifest's block rule to the zone's existing `http_request_firewall_custom` ruleset, preserving other rules. Scope it to exactly the five listed portfolio custom hosts. `ip.src.country ne "US"` covers unknown geography too. Do not exempt the webhook from geography: Cal outbound delivery must be proven US-originated. If genuine Cal traffic is foreign, stop activation and obtain a policy decision; no silent exception or alternative ingress is included. The Pages-only app's country requirement handles the `pages.dev` hostnames outside this zone rule.

## Ordered release and activation

1. Resolve provider-isolation authorization and capacity first. Freeze and review the redacted before/after configuration; stop on unrelated drift. Keep the original restrictive provider, shared owner policy and owner AUDs available for recovery.
2. Release the supporting branch through the existing reviewed PR/approved merge workflow. Never merge or deploy merely to collect evidence. For that first release, set each GitHub environment `ACCESS_ROLLOUT_STATE=bootstrap` and an explicit `ACCESS_BOOTSTRAP_DEADLINE` no later than **2026-11-12T08:00:00Z**. This is a finite public bootstrap period, not protected-site readiness. If the window expires, stop and resolve the rollout; do not extend it implicitly. The bootstrap contract requires actual portfolio HTML and health JSON, plus the existing Ask `400 validation_error` and unsigned Cal `401 invalid_signature` configuration contracts; login HTML and WAF denials fail.
3. Verify deployed `private, no-store` for HTML, hashed assets, photo and résumé, and purge existing public CDN cache entries before relying on protection. Remove conflicting cache rules; inspect effective live headers. Previously downloaded files cannot be recalled. Record the prior Pages/Worker versions for recovery.
4. After prerequisites, register and independently test providers without broadening existing apps. Create the new owner and visitor policies; update portfolio owner apps in place with pinned IdP and path cookies. Apply Pages owner protection, Cal bypass applications, and preview visitor app. Add the five-host WAF rule. Confirm signed-in owner access before closing the rollout window.
5. Complete the preview exercises below. Apply the production visitor app only after preview succeeds. Re-export all affected settings and verify no unrelated app/provider/policy changed. Record IDs, content digest, actor and time.
6. Set each activated GitHub environment `ACCESS_ROLLOUT_STATE=enforced` and remove its bootstrap deadline immediately. Run `node scripts/access-probe.mjs` with `ACCESS_PROBE_ENVIRONMENT=preview` or `production` from US egress. CI now requires an unfollowed HTTP 302 to `https://cold-union-464d.cloudflareaccess.com/cdn-cgi/access/login/<requested-host>`; HTTP 200 login HTML, wrong team/path and WAF 403 fail. This verifies the signed-out boundary only. Authenticated business health and real Cal delivery are separate release evidence, not replaced by the probe.

## Live acceptance evidence before declaring activation complete

- In cold US browsers, independently sign in with ordinary Google and intended Microsoft personal/work accounts; test root, every route, contact, Ask status/request, PDF and assets. Test Cloudflare independently if offered. Verify a signed-out direct asset/PDF request challenges rather than serving bytes. Record provider type and result, never tokens or personal payloads.
- In the same browser, visit visitor → owner → visitor and repeat API reads/mutations. Ordinary visitors must be denied owner pages and direct owner API calls even after visitor login; exact owner must succeed. Confirm current owner AUDs remain unchanged.
- Clear API cookies while keeping the page open; API failure must offer sign-in in a separate tab. Sign in there, return, reload and verify health/contact/Ask. Repeat with expiry, logout and warm browser/CDN caches. Verify session revocation and configured log retention in Cloudflare; do not invent the tenant's retention duration.
- From non-US and unknown-country test egress, verify denial for apex, www, preview and both API hosts, including a previously authenticated session, owner path and webhook. Check WAF events identify the expected rule and safely record no credentials.
- Test default Pages project URL, current immutable deployment, preview alias, a historical deployment and another branch alias. Only owner+US access is allowed. Test every Worker default/preview/version URL is disabled. Do not create deployments just for this test without authorization.
- Send genuine Cal-created/rescheduled/cancelled US deliveries to the exact configured URL. Confirm signature, booking persistence, deduplication and minimal stored fields; correlate country/rule events. Confirm unsigned POST rejects with `invalid_signature`, GET is 405, descendants/siblings are harmless, exact-origin OPTIONS is content-free and foreign OPTIONS is denied. A US curl unsigned 401 alone does not prove actual Cal delivery; a WAF 403 is failure, not health.
- Confirm bounded origin preflight with credentials on visitor and owner APIs. Exercise contact/Ask validation and successful authenticated use. Inspect actual health JSON under the authenticated session; do not follow login redirects in automated checks.
- Verify Access/WAF failure visibility, alert routing to the responsible human and the critical recovery steps below. Keep redacted exact-content evidence with the release record. External Power BI Publish-to-web reports and Cal-hosted pages remain independently reachable and are outside this gate; do not promise the portfolio gate restricts those external copies.

## Recovery

Keep a signed-in dashboard/operator session and redacted pre-change exports. If an owner locks out, use the dashboard to restore only the affected portfolio owner app's original provider/policy attachment and cookie settings, preserving AUD. Verify owner access before retrying. Roll back provider changes only after checking every relying app; shared provider or policy changes are not an authorized shortcut.

If visitor/provider or booking tests fail, stop activation and keep the protective boundary closed while diagnosing. A return to public access is a security-policy change requiring an explicit decision; do not automatically delete Access/WAF controls. Restoring a prior app deployment does not restore Cloudflare Access/WAF or database state. Restore reviewed configuration from snapshots and the known compatible Pages/Worker versions only within release authorization. Verify exact owner access, visitor denial, geography and signed Cal behavior again. Record the exercise; this written procedure alone does not prove recovery worked.
